# Native entity shadow compatibility witness

This folder contains host-only verification. It does not start or attach to Minecraft, edit installed packs, write game runtime files, or replace native shadow materials. The lifecycle owner controls one managed noactivation instance, server-side reversible floor edits, a frozen entity, passive captures, and cleanup.

The installed `3.10.0.467018` client's `vanilla/materials/shadows.material` is relevant: `shadow_front` and `shadow_back` write only stencil bit `1`, while `shadow_overlay` compares **all bits** using `Equal`, ref `1`, read mask `255`, write mask `0`. Its blend factors are `DestColor / Zero`. Therefore transport bits `64/128` do not share the native write bit, but can still affect the overlay's full-byte stencil comparison. `native_material_receipt(client_root)` hashes and checks these exact shipped definitions and the overlay shader. Source analysis does not establish the engine route used by a particular entity.

The documented client toggle is `factory.CreateModel(entity_id).SetEntityShadowShow(bool)`. It has no return value, and no public shadow getter or radius field was authenticated. The existing custom static BB cube may be used only if its real off/on/off shadow is visible. A stock `minecraft:pig` is a fallback candidate; public server `CreateControlAi(entity_id).SetBlockControlAi(False, True)` freezes AI and animation, and `GetBlockControlAi()` returning `False` confirms AI is blocked. Entity position, rotation, camera and receiver projections must also remain fixed.

For the known camera `(0,-58,-3)` looking mostly along +Z, the working bounded layout intersects its native screen ray `(520,550)` with ground plane `y=-59`, then places a 6×6 stone floor around that point at block `y=-60`. The caster shares this ground point's X/Z but its foot is at `y=-58.25`, hovering 0.75 blocks above the receiver. This separates the visible ground shadow from the projected body mask. The unshadowed guard lies farther behind the caster at local Z `+1.7..+2.2`, avoiding the moving player's screen area. The lifecycle owner backs up actual block values before edits and restores them afterward. The camera stays fixed, native outline/highlighter/UI/known RGBA fixture stay off, and weather/daylight are frozen.

Actual stock-client evidence in `.runtime/native-stencil-compat-20261119-r1/stock/shadow-recovery-r2-evidence` established the custom static cube's real native shadow: 377 positive receiver pixels inside the source ROI, 382 outside, and 60 at its boundary. The 16,127-pixel receiver replay, 3,770-pixel body guard and 481-pixel floor guard all had zero changed pixels. All 36 floor blocks were restored exactly. An independent recomputation is recorded in `.runtime/native-shadow-independent-audit-20261119-stock-r2/audit.json`. This is a visible native-only positive control; carrier-active byte-exact coexistence is a separate result. The earlier grounded attempt is retained as failed because its conservative body mask excluded the visible pig shadow and its left guard overlapped the player.

The actual carrier attempt in `.runtime/native-stencil-compat-20261119-r1/carrier/shadow-evidence` found a **native visual conflict despite intact data**. Exactly 196 shadow pixels changed inside the source ROI, with none outside. All 196 baseline shadow pixels whose transported symbol had bit `64` set changed; all 181 whose bit `64` was clear stayed within tolerance. Per symbol, `0`:88 unchanged, `1`:86 changed, `2`:93 unchanged, `3`:110 changed. The native and active off-state regions matched within two channel values. Mode 1 and mode 3 were independently decoded from the same diagnostic PNGs against the actual 65,536-byte input and passed all data/guard checks. All floor blocks were restored. The independent audit is `.runtime/native-shadow-independent-audit-20261119-carrier-r1/audit.json`. This establishes the measured bit-64 correlation and a failed native-shadow coexistence case; it does not prove a GPU capture of the exact stencil event or extend the observed conflict to bit128.

Before any acceptance capture, project known world receiver and unshadowed control patches with the public camera API and record their world points and projected pixels. Freeze a plan using:

```python
plan = make_plan(
    viewport=[720,1080], roi=[8,128,512,512],
    receiver_polygon=projected_receiver_points,
    body_bounds=projected_body_bounds,
    control_polygon=projected_unshadowed_floor_points,
    output_y=650)
```

The receiver polygon must cross the source ROI, the control polygon must be separate from it, and every region must lie above the reserved diagnostic output. The body region is excluded from the receiver and its core becomes an animation guard. `make_plan` records mask counts and a SHA-256. Masks are derived only from declared geometry, never from observed screenshot colors. Record this plan before capturing; modified plans are rejected.

Obtain a native-only **off → on → off** triplet and a carrier-active **off → on → off** triplet. Each toggle uses the documented native setter and waits for a render fence. `compare_snapshots(states)` separately requires requested flags `False/True/False`, one entity, fixed native position and camera, unchanged `receiver_revision`, and `static_entity` or `animation_frozen`. Successful setters do not establish visibility. Owner receipts must also retain rotation, frozen AI readback where applicable, receiver block readbacks and the frame/capture association.

`compare_shadow(off_before,on,off_after,plan)` requires achromatic darkening of at least 8 channel values on average and 4 in every channel, with at least 24 positive pixels inside and 24 outside the source ROI and positive pixels at its boundary. It checks the whole receiver off replay, unshadowed floor control and body guard independently. More than 1% of any region changing by over four channel values fails the stability gate, distinguishing receiver/background changes or animation from a shadow toggle. A setup without a visible witness fails; it is not interpreted as compatible.

`compare_coexistence(native_triplet,active_triplet,plan,payload_reports,actual_payload=experiment.payload)` retains both positive controls and compares **every declared receiver/body/control pixel** between native-only and carrier-active frames, allowing the existing restoration's stated two-value RGB quantization tolerance. Payload correctness remains byte exact: the host independently redecodes both complete mode 1 identity checks (65,536 addresses) and mode 3 raw checks (262,144 source samples covering 65,536 addresses) from the exact PNG files and actual host input bytes, including all guard pixels. Both must have zero errors, one 64 KiB identity and explicit unchanged resident native pages. Merely reporting `exact=True` cannot pass. The helper verifies that the shadow is preserved above `y=650` in those same diagnostic screenshots. Omitting the actual bytes deliberately fails. Owner execution must separately assert `compare_snapshots` and all managed capture/noactivation/freshness gates.

Run offline tests with `python -m unittest discover -s tools/integrated_shadow_fixture -p test_verify.py`. Synthetic tests reject missing shadows, receiver replay drift, animated body guards, whole-scene darkening, mutated plans, payload errors, and diagnostic screenshots where the real shadow is absent. They do not establish real native shadow acceptance.

Public sources queried through `minecraft_docs`: `api SetEntityShadowShow`, `api SetBlockControlAi`, `api GetBlockControlAi`, `api CreateEngineEntityByTypeStr`, `netease shadows.material`.

# Target block highlight follow-up (read-only)

The authentic public target-highlighter control is `factory.CreatePlayerView(level_id).HighlightBoxSelection(bool)`, with no return value. `Camera.PickFacing()` returns the center target's `type`, block `x/y/z`, `face`, and hit position. A host-driven demonstration can freeze a known target and camera, assert identical block readback and `PickFacing` target across off/on/off captures, and inspect **face interior** changes. No desktop input is required. Existing Video→Outline settings can leave wireframe visible, so line pixels alone do not establish the surface highlight; the docs also describe updates when the camera moves, so actual final-pose pixels must prove any toggle refresh.

The prior `ui3D.material` is relevant to world selection: official material-list documentation identifies `selection_XXX` as the selected block/entity effect and `selection_box` as the target wireframe. In installed assets, `selection_overlay` inherits `block_overlay`, whose stencil ref/read/write masks are `2`, using `NotEqual / Replace`; `selection_overlay` uses `DestColor / SourceColor`. This source family is not unrelated screen UI. However, the exact selection variant selected by `HighlightBoxSelection` in this client remains unproven until a visible toggle test. Selection bit `2` is disjoint from transport `192`, while the shadow's full-byte read mask includes both, so isolate shadow and selection tests first. Public queries: `api HighlightBoxSelection`, `api PickFacing`, `netease ui3D.material`.

`highlight.py` supplies the bounded face-interior verifier. Its `make_plan` requires the face to retain at least 64 pixels per ROI side after both an 8% geometric inset and a fixed three-pixel erosion, excluding thin/oblique wireframe-only false positives before capture. `compare_snapshots`, `compare_visible` and `compare_coexistence` mirror the shadow contract, with native `PickFacing` target and block readback receipts. `highlight_runner.run(experiment)` is an optional owner-only orchestration entry: back up and place two ordinary stone blocks, fix camera `(-.5,-58,-3)` at `(8,180,0)`, assert target `(-1,-59,-1)`, freeze its projected face and adjacent guard, test off/on/off, then repeat with the active carrier and independently decode the same complete diagnostic PNGs. It restores the blocks and original camera afterward. It performs no action on import and never starts/stops/activates the game or sends input.

The first detached-camera attempt returned `PickFacing == {'type':'None'}` and stopped at that gate, preserving `.runtime/native-stencil-compat-20261119-r1/carrier/highlight-evidence`. The documentation does not say that detached picking is universally unsupported; this is the observed result of that controlled attempt. Do not rerun its original helper: its post-pick client block readback used the server-only `GetBlockNew`, a path that was never reached in that failed attempt.

`attached_highlight_runner.run(experiment)` is the new bounded recovery for a fresh carrier before any dimension change. It backs up the server player foot/rotation and public camera position/rotation/anchor/offset/perspective. It backs up a 45-block platform and clear volume before edits, grounds the player at `(.5,-60,-3.5)`, and uses public `ResetCameraPos`, `UnDepartCamera`, `ResetCameraBindActorId`, first-person perspective and local player rotation. It reads the actual attached eye and forward vector, keeps the native pick range unchanged, and backs up/places a near target and adjacent guard based on the actual eye ray. The ordinary path changes 47 distinct positions. Actual `PickFacing` coordinates and the near-Z hit position must pass before a geometry plan is frozen. Its own client snapshot correctly uses `GetBlock(pos)`.

The attached recovery then uses the same native off/on/off and same-PNG complete 64 KiB checks. Independent cleanup operations attempt every restore even if one fails, and the result fails if player foot/rotation, camera settings or blocks do not match their backups. It restores the harness's known detached camera mode. This helper passes syntax checks and host regressions, including client-only `GetBlock` and failed-player-backup cleanup. The completed native acceptance is recorded below.

The first attached retry reached the correct native block/face but all world pixels were identical between off/on/off. The harness inherited `HideHudGUI(True)`; public documentation explicitly equates it with F1. `visible_hud_highlight_runner` then kept the frozen attached test and oracle unchanged while making HUD/crosshair visible. Both native and carrier-active face highlight positives passed, but the visible bottom slotbar covered 4,074 mode-1 guard pixels; the complete mode-1 data region still had zero errors. Both failed attempts remain preserved.

The final `selective_hud_highlight_runner.run(experiment)` keeps the global HUD visible so the world target highlight renders, while public `HideSlotBarGui`, `HideHealthGui` and `HideArmorGui` hide ordinary bottom widgets. It restores those widgets and the harness's known hidden HUD afterward. It does not change the attached source, Y650 layout, payload, geometry plan, pixel thresholds or verifier. Actual evidence is `.runtime/native-stencil-compat-20261119-r1/order-first-recovery-r2/attached-highlight-selective-hud-evidence`, independently audited in `.runtime/native-highlight-independent-audit-20261119-selective-r1/audit.json`.

All eight final PNGs passed fresh passive WGC/noactivation gates. Native and active off/on/off sequences each changed 156,460 face-interior pixels inside the source ROI and 34,260 outside, with 3,906 at its boundary. All 200,125 face/guard pixels were preserved within two channel values in every paired native/carrier state and in the same mode-1/mode-3 diagnostic PNGs. Independent decoding of the actual 65,536-byte input, all 262,144 raw symbols and every guard pixel produced zero errors. Payload identity, native pages and generation stayed fixed across all eight frames. All 47 blocks, player foot/rotation and camera settings were restored; HUD restoration was requested successfully. The failed attached, HUD-visible and final evidence trees were unchanged during independent audit. This proves the stated ordinary native target-highlighter case under these controls, without claiming which exact `selection_overlay` GPU variant the engine selected.
