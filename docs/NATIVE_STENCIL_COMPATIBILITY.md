# 原生渲染与 stencil 数据通路共存验证

本轮在网易版 Windows OpenGL 3.10.0.467018 运行 64 KiB 数据通路。实机使用一个受管实例逐项运行，常规视口为 720×1080，帧率上限为 60 FPS。普通序列帧、原生阴影和附魔库存分别使用原生接口和实际可见对照。逐像素检查基于被动 WGC，数据检查覆盖宿主提交的全部 65,536 字节和对应的 262,144 个源符号。此前的实体描边和普通矩形 UI 裁剪结果见[同帧数据报告](SCENE_CODEC_512K_RESEARCH.md#同帧恢复与数据消费)。

## 已复现的冲突

| 用例 | 原生画面 | 数据 |
|---|---|---|
| 普通序列帧 | 原生材质下 8 个对照通过。加载测试数据包后，常规／加法、点／线性四条路径，在源区内外、载荷开关两种状态下共 16 个用例全失败。关闭载荷后仍失败。 | 34 张完整数据诊断均零错 |
| 实体阴影 | 原生基线 759 个阴影像素。启用数据后，源区内 377 个阴影像素少了 196 个，源区外 382 个保持。 | 对应的两张阴影和数据同屏截图完整读回零错 |
| 维度切换 | 从主世界进入下界并返回，原生维度和实际玩家位置已恢复。这个原型没有维度重建逻辑。 | 两地在不重新绑定时都出现 65,280／65,536 个字节错误 |

序列帧使用安装版四条共享材质的 `no_depth_test` 变体。替换资源后，普通序列帧会受同一材质的顶点、混合、深度及模板测试配置影响。独立像素复核确认两种包的所有固定 OFF 背景像素完全一致；数据包中的普通效果开启后，样本仍与关闭时一致。附加效果的独立材质需要实机确认实际绘制顺序。一种候选是网易版粒子的显式独立材质名和公开分层接口，仍须先确认它能在雨后、后处理前渲染。

阴影缺失像素与源数据模板位完全对应。377 个源区内的基线阴影像素中，bit 64 为 1 时 196 个全部消失，bit 64 为 0 时 181 个全部保留。原生阴影材质写入 bit 1，显示阴影的材质通过掩码 255 检查模板值。修复后需重新核验阴影绘制与模板写入的顺序。

## 已通过的对照

- 沿用前一轮同一数据通路的实体描边、矩形 UI 裁剪和两者同屏结果。固定背景下，载荷开启前后的 1,369 个描边像素位置相同。独立复算 22 张裁剪截图，每帧 5,952 个检查像素零错；裁剪与描边同屏时的全量数据也通过。裁剪用例覆盖不透明图片的普通矩形裁剪，诊断期间 UI 保持可见，以同帧截图与状态为准。

- 原生物品渲染器的普通、附魔和空槽对照在关闭、开启载荷时均通过。使用真实创造背包进一步对照时，关闭、开启载荷后分别有 67、66 个附魔弓像素随时间变化，同屏普通槽和空槽均无变化。测试物品备份已逐槽恢复。

- 打开和关闭原生背包与暂停菜单后，未经重新绑定便完整读取到同一份 64 KiB；继续检查符号和保护区也通过。

- 源区开启、关闭、再开启时，已知参考图关闭后逐像素恢复。关闭几何和清除四边形后，仅启用晚期模板读取器，读回全零。搬移源区、将视口变更到 1120×1080 并变更源区长宽、恢复原视口，三次均复用原载荷页并通过全量读取。

- 目标方块高亮使用第一人称实际选中方块。离体相机无法通过公开接口拾取方块，绑定玩家后必须保持 HUD 可见才能得到高亮阳性对照。最终验证保持准星和高亮，临时隐藏底部常规 HUD 部件，沿用原诊断区域。填充高亮覆盖 190,720 个像素，穿过源区边界。开启载荷前后，整块高亮和保护区共 200,125 个像素的逐通道差异最多为 2；同一帧的 65,536 字节和全部 262,144 个源符号均读回零错，数据保护区零错。已证实填充高亮的可见路径。安装版 `vanilla/materials/ui3D.material` 的 `selection_overlay_level` 与 `selection_overlay_opaque` 都能在不透明石块内部输出相同的颜色，现有证据无法确定引擎绑定的具体材质变体。独立线框未验收。

- Windows MSAA 请求值 1× 和 4× 各使用同一 720×1080、64 KiB 载荷。首次实例初始化时读取到空的摄像机方向，两个失败启动证据均保留。重测将相机切换和创建锚点放到不同帧。晚期载体着色器出现了对应的两种原生编译分支，256 个见证像素分别全中各自的颜色，直接／依赖读取、262,144 个源符号和边界像素全部正确。系统设置已恢复。

## 资源包共存

额外测试包提供与安装版逐字节相同的 `sfx.material`，与数据包中的同名文件发生真实冲突。两次启动的实际世界资源包 UUID 顺序相反。两种顺序中，额外测试包独有的 UI 图样都被实际绘制，每次启动共检查 42 帧，每帧的 1,344 个见证像素都精确匹配。两种顺序都观察到数据包的材质行为：各有 8 个普通序列帧对照消失，16 次完整数据和保护区诊断零错。调整世界资源包顺序未恢复普通序列帧，底层资源解析优先级仍未确定。

## 原生后处理

景深原生着色器执行已证实。设置非零模糊后，262,144 个参考像素中的 262,142 个改变超过 2 级，恢复零模糊后回到原像素。零模糊对照中，恢复阶段的 RGB 在允许误差内。景深阶段实际输出的 262,144 个像素与恢复前的编码 RGB 完全一致。晚期直接和依赖读取继续逐字节正确。原生景深需要修正输入路径后重新验收。

Bloom 在原生启动定义里报告开启，启用载荷后的晚期全量读取也通过。两次启动均未观察到原生 Bloom 响应。复测临时把宿主的两项 Bloom 强度从 0 改为 1，并在安装自定义处理链之前比较同 RGB 的不透明、可变 alpha 和恢复不透明三张图。262,144 个参考像素中没有 RGB 变化超过 2 级，恢复不透明的参考逐像素相同。安装处理链后的重复检验同样没有阳性。测试记录保留 Bloom 原生阶段未证实的判定，系统设置已恢复。

## 移动端

ADB 没有发现 Android 设备。宿主装有 MuMu，命令行返回空实例列表。手机实机用例仍待设备和可部署的网易版客户端。测试固定为 60 FPS 上限，本轮兼容用例没有单独采集帧时间。

## 原始证据

可用[证据索引](evidence/native-stencil-compat/summary.json)定位逐项原始收据、独立复算结果、三组画面对照和停止回执。索引包含 SHA-256。原始 PNG、日志和游戏数据留在本机的 `.runtime`。两档 MSAA 和 Bloom 的临时设置已恢复，本轮所有受管实例已停止。

普通序列帧、阴影、景深和维度切换仍有已复现的兼容问题。当前概念验证可以在已通过的用例里完整传输 64 KiB，alpha 打包应等这些冲突修复及复测后再接。
