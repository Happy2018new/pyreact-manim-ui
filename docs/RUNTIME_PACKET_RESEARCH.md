# 运行时 Python → shader 大数据传输研究

本轮目标是验证**大量运行时数据的真实传输、正确性和成本**。游戏 Python 生成数据，shader 实际消费，再由后台 WGC 截图逐字节核对；接口返回 True、离线生成资源和宿主 CPU 编码成功均不算实机传输成功。

本文保留早期单列 atlas 实验及原始测量。后续二维布局与新的限帧条件下的结果见 [二维传输研究](RUNTIME_PACKET_2D_RESEARCH.md)，两轮结果分别记录。

## 已得到的结论

1. **累计 100,000 个 float32，400,000 字节，实机分块传输并校验通过。** 共 17 批，每批替换同一个 atlas；全部 417,792 个协议字节（含批次头和清零尾部）精确一致，按批重组的有效数据 SHA-256 为 `86d2a846d69904e38d7ac3823cd4ca5e1546597295a403f69a3d7bc14b1321fc`。期望值由独立标准库公式生成，未使用上传后的 words 作为期望值。
2. **已验证的最大单批容量为 24,576 字节，即 24 KiB。** 加 16 字节头后最多容纳 6,140 个 float32。17 批累计成功不意味着 shader 同时持有 100,000 个数；旧批次会被覆盖，也没有验证跨批保留计算状态。
3. **本轮 24 KiB 通路成本很高。** 它需要 1,024 个 producer pass、1 个 consumer pass，每次全量上传调用 2,048 次 `SetParameter`。当时用户在睡觉期间主动设置了外部限帧，基线约 20 FPS；在这一条件下，静态约 18.57 FPS，每帧重建并上传后约 13.02 FPS。它可用于研究有界分块数据，但不适合作为已解决的大容量高频 buffer。
4. **BBE 的单像素载体可传少量参数。** 一个透明 Image 的 `SetSpriteColor` 为紧邻绘制提供三个 uint24，合计 9 字节；64 个载体、576 字节的静态及动态传输准确。256／1,024／4,096 个载体的包在首次 `CreateUI` 阶段失败，未得到其容量传输成功的证据。

研究源码在 [runtime_packet_probe](../tools/runtime_packet_probe/README.md)，精简结果和哈希在 [summary.json](evidence/runtime-packets/summary.json)。原始截图、完整逐字节报告、命令、启动回执均保留在 `.runtime/runtime-packet-study/`，不加入发布包。本轮未改变生产动画、生产资源包或播放接口。

## 数据通路与协议

BBE 参考方案里的“单像素”是一个绘制状态载体：Python 设置浮点颜色，下一次绘制读取 `CURRENT_COLOR`。它不把任意数组写入一张 1×1 PNG。RGB 各存 `uint24 / 2^24`，shader 恢复三个整数，再拆成九个 byte。恢复整数时不能加 `0.5`，否则 float32 在 `2^23` 以上会把部分奇数错误舍入。

实测还发现普通 HUD 绘制会干扰载体顺序。根节点 layer 为 0 时，八行中一行输出了非法域的洋红色；根节点改为 1000、隔离绘制顺序后所有字节准确。默认颜色 `1.0` 被视为非法载荷，不能误认成最大 uint24。

大容量实验采用后处理 atlas：每个 producer 接收两个 vec4，保存八个 uint24，合计 24 字节，写入自己的一行并复制上一 producer 的其他行。consumer 通过纹理随机索引访问 page／word／byte。1／4／16／64／256／1,024 页均有实际画面的全字节验证，64 和 1,024 页另有循环移位查询验证。

实际 3.10 客户端将 `EXTRA_VECTOR4` 用于屏幕信息，早期把载荷放在该槽时 GPU 得到黑白错误结果，即使 `GetParameter` 仍返回请求值。因此修订格式只使用 U1 存 page 元数据、U2/U3 存载荷。请求的 RT 为 `32 × (4 × pages)`，比例限制在 1 以内；1,024 页在本次窗口中实际为 `32 × 1305`，并非 `32 × 4096`。

数值协议按 little-endian float32 保存位型；前 16 字节是四个 uint32：magic、标量数量、有效字节数、generation。长度缩短时显式清零全部剩余空间，超容量在首个 SDK 调用前拒绝。部分上传失败会停用整个链并标记无效，防止混合批次被当作成功结果。

## 正确性与对照

| 实验 | 实机检查范围 | 结果 |
| --- | --- | --- |
| CURRENT_COLOR 载体 | 8／32／64 个，静态及逐渲染帧更新后的冻结末帧 | 72／288／576 字节精确一致 |
| atlas | 1／4／16／64／256／1,024 页 | 每个案例所有字节精确一致，最大 24,576 字节 |
| 索引查询 | 改变 row／word／byte 偏移，包含回绕 | 指定查询的全部字节精确一致 |
| 变长浮点序列 | 0、1、5、6、7、1,532、3、0 个数，再测特殊值 | 九张截图共 55,296 字节精确一致，头部、位型、零尾部独立复核通过 |
| 大数组分块 | 100,000 个 float32，17 批 | 400,000 个有效数据字节重组后哈希一致 |
| 超容量 | 256 页中上传 1,533 个 float32 加头部 | 拒绝；此前 words 保持不变 |

特殊值覆盖 `-0.0`、正负分数、很大／很小有限数、最小正规数和最大有限 float32。它证明 float32 **位型能够传输**，尚未证明 shader 内已将这些位型还原为任意浮点算术值。宿主截图解码只是验证手段，不是游戏 Python 的 GPU 读回接口。

显式连线另外做了隔离对照：关闭旧 producer／display，只启用两个不依赖输入纹理的单页源 A、B 和唯一 consumer C，执行顺序 A < B < C。C 未连接时与 A 有 21／24 字节不符；首次连接 A→C 后 24 字节全对。只修改 A 时 C 跟随新 A；只修改 B 时 C 保持 A；再修改 C 查询，输出对应置换。此结果支持显式指定源确实有效。

早期“改接首个 producer”和“新增未连接 consumer”两次对照仍显示完整 atlas，但当时旧 display 未关闭，且重连替换、未绑定纹理的默认内容均无公开保证。这两次不计作有效缺链负控。后来只启用未连接 consumer 的单独实验仍有一行错误，不能将未连接内容视为可靠数据源。桌面 OpenGL 的确定错误纹理对照单独通过，不与这些游戏结果混用。

## 性能测量

设备为 RTX 4060 Laptop GPU，客户端 `3.10.0.448891`。后台 noactivation 实例，WGC 为 2251×1305，逻辑 UI 为 563×327。当时用户在睡觉期间主动设置了外部限帧，约 20 FPS 的基线来自这一限帧条件，不能归因为后台运行。游戏关闭无限帧率并配置了 60 FPS 上限；这个配置值不证明实际达到 60 FPS。下表保留当时测量原值，也不能据此推导解除外部限帧后的性能。

| 通路 | 单次载荷 | CPU 生成 p95 | SDK 上传 p95 | 平均渲染间隔 | 引擎平均 FPS |
| --- | ---: | ---: | ---: | ---: | ---: |
| 8 个载体 | 72 B | 0.154 ms | 0.121 ms | 50.02 ms | 20.03 |
| 64 个载体 | 576 B | 0.225 ms | 0.216 ms | 50.00 ms | 20.02 |
| 64 页 atlas | 1,536 B | 0.472 ms | 0.253 ms | 50.00 ms | 20.01 |
| 256 页 atlas | 6,144 B | 1.751 ms | 0.855 ms | 50.00 ms | 20.01 |
| 1,024 页 atlas，静态 | 24,576 B | 0 | 0 | 54.06 ms | 18.57 |
| 1,024 页 atlas，逐帧更新 | 24,576 B | 12.556 ms | 6.132 ms | 75.76 ms | 13.02 |

动态数据由游戏 Python 每个渲染事件重新生成并提交。SDK 时间是 CPU 侧调用耗时，未等待 GPU 完成；生成时间包括打包。基准运行 12–15 秒，预热 1 秒；1,024 页动态测试包含 185 个预热后上传样本。跨越终止时刻的长帧也计入，异常会记录 failed，不丢弃为“无样本”。引擎 FPS 与相邻事件间隔是两组采样值，不强制互为倒数。

每项动态基准只对停止更新后的最后一批做全部像素验证；未核验运行中的每一帧。100,000 数分块实验则对每一批的冻结画面都完整校验，约 39.91 秒墙钟时间包含 17 次 RPC 和 WGC，不是传输吞吐测试，不能用 `400000 / 39.91` 当作带宽。

另在真实 CPython 2.7.13 宿主中只测编码／解码，10,000／30,000／60,000／100,000／200,000 个 float32 的编码中位耗时为 10.06／28.67／57.68／92.15／178.82 ms。这些数据**未调用 SDK、未传入游戏或 GPU**；不能把 800,000 字节 CPU 编码成功写成 800,000 字节 GPU 上传成功。

## 失败边界与后续路线

256、1,024、4,096 载体的失败发生于首次 UI 创建，尚未开始批量写载荷。去除未使用的 block fallback、收拢隐藏控件初始位置后，256 仍失败，64 成功。未确定具体根因，不将其写成官方 UI 上限或内存不足。

早期研究包还错误覆盖了全局 `graphics_settings/post_process.json`，移除了引擎内置效果，导致原生断言。已改成保留内置定义并动态添加独立效果；builder 会拒绝带旧全局覆盖的输出，避免再次沿用故障包。

公开资料中未找到可直接上传任意 bytes／数组到 GPU texture 或 buffer 的通用接口。`SetEntityUIExtraUniforms`、`SetParameter` 仍是逐组参数调用，不能当作批量上传接口。

更大单批的下一优先方向是**单张运行时数据纹理**，见 [候选实验](../tools/runtime_packet_probe/BULK_TEXTURE_CANDIDATE.md)。RGB8 的 128²／256²／512×544 纹理分别可载 48／192／816 KiB，尺寸本身不大；阻碍是资源路径发现和持续刷新。旧 PNG 通路已证实预置路径首次读取准确，但覆盖后不刷新，只有全材质重载后更新，不能直接用于每帧传输。RawPath 的原版 binding 入口与此前失败的 `SetSprite` 入口不同，新候选仍未实施，不提前宣布成功。

对本项目的当前建议是保留离线几何／字体／图片资源，用少量运行时参数驱动变化。几 KiB 级分块更新可以继续研究；不要把 1,025-pass 的实验直接接入两部动画。若需求是 shader 同时随机访问几十万项、每帧全量更新，当前研究尚未给出满足该目标的通道。

## 复现与维护

资源生成、受管启动、数据上传、后台截图、固定坐标逐字节验证分别由 `build_probe.py`、`host.py`、`run_case.py`、`verify_capture.py` 承担。`run_numeric_stream.py` 对已完成 setup 的 atlas 执行完整分块序列；`verify_numeric_sequence.py` 可离线独立重查九组浮点截图。先读工具 README，再选择新的隔离输出目录，不覆盖既有证据。

68 项相关回归全部通过、无跳过，其中七项执行桌面 GPU 着色器；覆盖 float32 协议、容量、损坏／错批次／缺页拒绝、错误调用后的链失效、事件注销、UI 与后处理互斥。MCDK review 识别到六个实际行为包模块，零 warning/risk；仅有参数数量的 hint。所有实机操作绑定 `manim-runtime-packets` owner，本轮自建实例测试结束后已停止，没有操作其他项目游戏。
